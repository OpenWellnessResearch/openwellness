Facts the ADRs must reflect (verified in code by the planner):
- `BaseEntity.id` already defaults to `str(uuid4())` (backend/core/src/openwellness_core/domain/models/base_entity.py). Legacy Mongo ids are 24-hex ObjectIds, and Couchbase ids are Sync Gateway document ids. Python 3.12 has no stdlib uuid7.
- `BaseOwnerEntity.created_at` / `updated_at` are `float` from `time.time()`, with int tz-offset fields. Some domain models use `datetime` instead. Enumerate them all with `grep -rn "datetime" backend/core/src/openwellness_core/domain/models`. At planning revision (2026-10-30) the declared datetime fields are exactly 10: `Admin.time_created`, `App.time_created`, `Device.time_created`, `Fitbit.time_created`, `Participant.time_created`, `Study.time_created`, `Study.time_updated`, `StudyMessage.time_created`, `User.registered_at`, `User.time_created`. The Task 2 field check derives the same set from the source and compares it with the ADR table. Wire conversion is `epoch_to_rfc3339` / `rfc3339_to_epoch` in backend/api/src/openwellness_api/common/timestamps.py.
- Legacy archive behavior: Mongo `archive()` copies the document into `{collection}_archive` and leaves the original in place; Couchbase writes a separate `<Type>Archived` document. In both, the original stays readable, and `unarchive()` deletes the copy. Routes map DELETE to archive, `:undelete` to unarchive and `:purge` to a hard delete.
- Current tokens: HS256 signed with API_AUTH_JWT_SECRET (backend/api/src/openwellness_api/auth/token_service.py). The claims are iss, sub (user id), aud, iat, exp, jti, typ="access", participant (bare pid from roles.participant.pid) and roles (the list of role keys). The default access TTL is 900 s (API_AUTH_ACCESS_TTL_SECONDS), with 30 s leeway. Refresh tokens are random, stored only as sha256 hashes, and rotate single-use (auth/session_store.py).

    - this is a one-way door: the column type and client-generated ids are baked into the schema and the mobile app

    0002, with `Decisions: D-12`.

    Decision:
    - every timestamp column in Postgres, including created_at, updated_at, deleted_at and the auth-table times, is `double precision` epoch seconds
    - the domain keeps float epochs
    - the wire stays RFC 3339 through epoch_to_rfc3339 / rfc3339_to_epoch
    - adapters convert domain `datetime` fields and the refresh-session datetimes to and from epoch seconds at the boundary
    - include a table with columns `Model | Field | Type`, one row per domain field typed `datetime` found by grep, with the model class name and the field name each in backticks (for example a row starting `` | `Participant` | `time_created` | ``); no other table in 0002 may start a row with a backticked capitalized name, because the field check below reads every such row
    - the tz-offset int fields stay as is

    Consequences:
    - no timezone ambiguity in storage
    - sub-microsecond precision is not guaranteed
    - this is a one-way door: the column type spans about 37 tables

    0003, with `Decisions: D-07, D-08, D-09, D-10`.

    Context: today's legacy archive is a copy that leaves the original readable.

    Decision:
    - DELETE (archive) sets `deleted_at` (epoch seconds per ADR 0002) and keeps the row
    - every read excludes rows with deleted_at set unless the caller asks for them (AIP-164 `showDeleted`)
    - `:undelete` clears deleted_at, indefinitely: there is no auto-expiry and no retention job (D-07)
    - `:purge` is admin-only (D-08) and is a hard row delete with no scrub and no tombstone (D-09)
    - sync streams filter `deleted_at IS NULL`, so archive removes the row from devices, undelete brings it back, and purge relies on PowerSync's delete op; Phase 6 verifies the remove-on-transition (D-10)
    - the legacy Couchbase/Mongo backend keeps its current copy-based behavior behind the legacy flag and does not support offline sync: Mongo archive copies the document to `{collection}_archive` and leaves the original readable, Couchbase writes a separate `<Type>Archived` document, and unarchive deletes the copy (write the `{collection}_archive` form literally)

    Consequences:
    - purged research data cannot be recovered, which is why purge is admin-only (one-way)
    - archived rows cost storage until purged

    Add rows for 0002 and 0003 to the README index.
  </action>

    - access tokens are JWTs signed with EdDSA (Ed25519), carrying a `kid` header

    - dashboard, mobile and PowerSync verify through the JWKS
    - key rotation needs a documented procedure (Phase 12)
    - costly to reverse, since three verifiers depend on it
