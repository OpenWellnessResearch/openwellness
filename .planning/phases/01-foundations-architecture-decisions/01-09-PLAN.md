Facts verified by the planner:
- RESOURCE_MODULES (backend/api/src/openwellness_api/resources/__init__.py) has 36 modules. Every one exposes the same seven operations: get, list, create, patch, delete (archive), `:undelete` and `:purge`.
- 26 modules mount under `/v1/users/{user}/...`: actigraph_record, asset, card, condition, daily_state, fitbit_heart_record, fitbit_record, fitbit_sleep, fitbit_sleep_session, fitbit_weight, goal, job_rule, message, message_draft, meta_data, participant_group, physical_activity, post, session, shared_goal_progress, survey_result, user_food, user_settings, user_sleep, user_stress, weight.
- 7 modules are top-level: admin (/v1/admins), app (/v1/apps), conversation (/v1/conversations), device (/v1/devices), fitbit (/v1/fitbits), study (/v1/studies), user (/v1/users).
- 3 modules are study-scoped under `/v1/studies/{study}/...`: participant, study_message, study_settings.
- Unauthenticated by design: `/v1/auth:*` custom methods and `/healthz`.
- BaseOwnerEntity carries `study_id`, so "coach (in-study)" on a users/{user}/... row means the record's study_id is in the caller's coach_studies claim.
- The refresh flow re-reads the user record and re-mints roles (AuthService.refresh_token calls `user_repo.get_by_id`, then `_roles_list`), so coach claims refresh at every access-token renewal. Defaults: access_ttl_seconds=900, jwt_leeway_seconds=30 (AuthSettings).
- The legacy `Admin` entity (domain/models/admin.py) has a `study_ids` list. Per D-03 it is not the v1 membership source.
- `Fitbit` holds OAuth access and refresh tokens (domain/models/fitbit.py).

    Write 0006 with `- Status: Accepted` and `- Decisions: D-02, D-03, D-04`.

    Context: the research default was a role gate; the developer chose study scope.

    Decision:
    - a coach acts only within the studies listed at `roles.coach.studies` (a list of study ids) on their User record
    - admins edit that list, and a coach cannot edit it
    - the access token carries it as the `coach_studies` claim (list of strings); a claim name distinct from `roles` keeps role keys a flat list
    - no StudyStaff/membership entity exists in v1 (deferred)
    - admins are global and need no study list
    - the legacy `Admin.study_ids` field is not read for authorization
    - staleness: claims are re-minted from the user record at every refresh, so a removal takes effect within at most API_AUTH_ACCESS_TTL_SECONDS (900 s default) plus jwt_leeway_seconds (30 s); an admin who needs immediate effect revokes the coach's sessions

    Consequences:
    - every coach-reachable query filters by study_id in coach_studies
    - Phase 6 sync policy uses the same claim
    - costly to reverse

    Add the 0006 row to the README index.
  </action>

    Write 0007 with `- Status: Accepted` and `- Decisions: D-04, D-05, D-06, D-08`.

    `## Context`.

    `## Decision` states:
    - Denials (D-05): anonymous gets 401; authenticated but missing role gets 403; wrong owner or outside the caller's study gets 404 (anti-enumeration).
    - Deny by default: a method not listed in a cell is denied.
    - Scope (owner binding per ADR 0005, coach study filter per ADR 0006) is applied before any user-supplied filter= expression and can never be widened by it.
    - The admin column is global (D-04) and is the only column that may hold purge (D-08).
    - A rule table, used for every users/{user}/... row, maps the ADR 0005 data class to the participant-self and coach cells:
      - participant-data: participant-self gets get, list, create, patch, delete, undelete; coach gets get, list
      - server-ingested: participant-self gets get, list; coach gets get, list
      - study-content: participant-self gets get, list; coach gets get, list, create, patch, delete, undelete
      - coach-authored: participant-self gets get, list; coach gets get, list, create, patch, delete, undelete
      - admin gets all seven methods in every class
      Write the rule table's first column with the hyphenated class names in backticks so the policy check below does not mistake it for a module row.

    `## Policy table` has columns `Resource module | Route | Scope | anonymous | participant-self | coach (in-study) | admin`:
    - one row per RESOURCE_MODULES entry, module name in backticks
    - cells are a comma-separated subset of get, list, create, patch, delete, undelete, purge, in that order, or none
    - users/{user}/... rows come from the rule table using each module's class in 0005
    - conversation and study_settings rows follow their 0005 class, with participant-self meaning "within the caller's study"
    - fixed rows for the rest (least privilege; a later ADR amendment widens a cell when a client needs it):
      - `admin`: participant-self none, coach none
      - `app`: participant-self none, coach none
      - `device`: participant-self get, list (device.participant_id equals the caller's participant claim); coach get, list (in-study)
      - `fitbit`: participant-self none, coach none (the record holds OAuth tokens)
      - `study`: participant-self get (the caller's own study); coach get, list (studies in coach_studies)
      - `user`: participant-self get (the {user} path equals the token sub); coach none
      - `participant`: participant-self get (own record); coach get, list, patch
      - `study_message`: participant-self get, list (own study); coach get, list, create, patch, delete, undelete
      - admin is all seven methods on every row

    A second small table `## Unauthenticated endpoints` lists `/v1/auth:*` and `/healthz` as the only anonymous surface.

    `## Consequences` notes:
    - the route-enumeration 401 test in Phase 2 checks this table
    - the mass-assignment caveat: self patch on any row may not change owner, study_id, roles or audit fields (Phase 2 field allowlist)

    Add the 0007 row to the README index.
