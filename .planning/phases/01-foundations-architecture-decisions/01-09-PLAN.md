Facts verified by the planner:
- RESOURCE_MODULES (backend/api/src/openwellness_api/resources/__init__.py) has 36 modules. Every one exposes the same seven operations: get, list, create, patch, delete (archive), `:undelete` and `:purge`.
- 26 modules mount under `/v1/users/{user}/...`: actigraph_record, asset, card, condition, daily_state, fitbit_heart_record, fitbit_record, fitbit_sleep, fitbit_sleep_session, fitbit_weight, goal, job_rule, message, message_draft, meta_data, participant_group, physical_activity, post, session, shared_goal_progress, survey_result, user_food, user_settings, user_sleep, user_stress, weight.
- 7 modules are top-level: admin (/v1/admins), app (/v1/apps), conversation (/v1/conversations), device (/v1/devices), fitbit (/v1/fitbits), study (/v1/studies), user (/v1/users).
- 3 modules are study-scoped under `/v1/studies/{study}/...`: participant, study_message, study_settings.
- Unauthenticated by design: `/v1/auth:*` custom methods and `/healthz`.
- BaseOwnerEntity carries `study_id`, so "coach (in-study)" on a users/{user}/... row means the record's study_id is in the caller's coach_studies claim.
- Create on users/{user}/... stamps `owner` from the {user} segment (`stamp_audit` in common/handlers.py) but takes `study_id` from the request body, and the Update schemas accept `study_id` (for example schemas/weight.py). A predicate that reads only the record's study_id would therefore let a coach in study A write a record with study_id A for a participant in study B, which then reaches B's participant through owner-keyed reads and sync. coach-study must also check the owner's study on writes. The same body-supplied study_id reaches participant-self creates (and conversation create takes both owner and study_id from the body, resources/conversation.py), so a participant in study B could file a record under study A that coach-study reads then show to A's coaches; the study binding on create is therefore a caller-independent write rule (`study-binding`), not part of one column's predicate.
- The study-scoped routers already require the stored study binding to equal the {study} segment: participant `_fetch` compares `study_id`, study_message calls `check_parent(..., parent_field="study_id")`, study_settings calls `check_parent` on owner; create stamps it from the segment.
- The refresh flow re-reads the user record and re-mints roles (AuthService.refresh_token calls `user_repo.get_by_id`, then `_roles_list`), so coach claims refresh at every access-token renewal. Defaults: access_ttl_seconds=900, jwt_leeway_seconds=30 (AuthSettings).
- The legacy `Admin` entity (domain/models/admin.py) has a `study_ids` list. Per D-03 it is not the v1 membership source.
- `Fitbit` holds OAuth access and refresh tokens (domain/models/fitbit.py).
- Study sources per record (verified by introspection of openwellness_core.domain.models): all 26 users/{user}/... domain classes plus Conversation and StudySettings subclass BaseOwnerEntity (`owner`, `study_id`). `Participant` has exactly one `study_id`. `StudyMessage` has `study_id`. `Study` is keyed by its id. `Device` has `participant_id` only, and no study id. `User`, `App`, `Admin` and `Fitbit` carry no study id.
- The ADR 0004 claim set (iss, sub, aud, iat, exp, jti, typ, participant, roles, coach_studies) has no study claim for participants, so a participant's study must be derived server-side from the Participant record named by the participant claim.
- The study_settings router calls `check_parent` with its default `parent_field="owner"` against the {study} segment (resources/study_settings.py), so StudySettings.owner holds a study id. ADR 0005 records this per entity.
