  <decision>What `owner` holds on participant-owned records, and therefore which token claim Phase 2 binds to {user} and what Phase 6 streams key on</decision>
  <context>
    This is a one-way door (D-01). Once Postgres rows (Phase 4 and 5) and PowerSync stream predicates (Phase 6) key on owner, changing it needs a data migration of every owner-scoped row plus a stream rewrite.

    Evidence found so far points to the participant id: the BaseOwnerEntity docstring, Fitbit ingestion setting owner=pid, sleep-session ids built from owner, and test fixtures using participant-style owners.

    The API path segment is nevertheless named users/{user}, and the token sub is the user id. Review docs/adr/0005-owner-semantics.md, especially the Entity classification table. The table drives every cell of the authorization policy table in plan 01-09.
  </context>
  <options>
    <option id="option-participant">
      <name>owner = participant id (Participant.id); bind the token participant claim to {user} on users/{user}/... routes</name>
      <pros>Matches legacy data and the server-side ingestion code; no data migration; one binding rule for all participant-owned data; streams key on the participant claim</pros>
      <cons>The users/{user} segment carries a participant id on owner-scoped routes but a user id on the top-level User resource; this is documented, not fixed, because the /v1 wire contract is frozen</cons>
    </option>
    <option id="option-user">
      <name>owner = user id (User.id); bind the token sub to {user}</name>
      <pros>Matches the path name and the token sub; one id space for routes</pros>
      <cons>Contradicts the legacy data and the ingestion code (owner=pid), so every legacy owner value needs rewriting; server integrations must look up the user per record</cons>
    </option>
    <option id="option-mixed">
      <name>Per-entity: keep whatever each entity actually stores, as listed in the classification table</name>
      <pros>No migration even if the evidence shows a genuine mix</pros>
      <cons>Two binding rules in Phase 2 and two predicate shapes in Phase 6; more room for IDOR mistakes. Choose this only if the evidence really is mixed</cons>
    </option>
  </options>
