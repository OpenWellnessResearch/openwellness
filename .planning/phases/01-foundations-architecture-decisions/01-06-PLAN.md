<objective>
Put refresh-session persistence behind a datastore-neutral `RefreshSessionRepository` port in core, with a Mongo adapter that keeps today's document shape, proven by contract tests (FOUND-05, first half). Plan 01-11 then moves the API's `RefreshSessionStore` onto the port and wires it through the composition root.

Purpose: Phase 3 adds the refresh grace window to one policy implementation, and Phase 4 adds a Postgres adapter for the same port. The security logic is not duplicated per datastore (research ARCHITECTURE.md, "Auth persistence").
Output: The port with its record type, the Mongo adapter and its contract tests. Nothing consumes the port yet.
</objective>

Facts verified by the planner:
- session_store.py today builds the refresh-session document in `create`, runs the CAS as a conditional `update_one` with a matched_count check, revokes with `update_one` / `update_many`, coerces datetimes with `_as_utc`, and creates the four indexes in `ensure_indexes` (OperationFailure re-raised as RuntimeError). This plan copies that persistence logic into the adapter; plan 01-11 deletes the store-side copies.
- test_session_store.py (16 tests) wraps mongomock collections to inject a lost CAS race (a wrapped update_one) and a failed child insert (a wrapped insert_one). The adapter must call exactly those collection methods so the wrappers still bite once plan 01-11 moves the store onto the port.
- The collection name is chosen by the caller today (`AuthSettings.refresh_collection`, env API_AUTH_REFRESH_COLLECTION, default "auth_refresh_sessions"). The adapter therefore takes a collection handle and never names a collection.
- `object_id_or_none` exists in mongo_base_repository.py (plan 01-03).
- Design note: `RefreshSession` lives in the port module as the port's record type, not in domain/models. It is an auth persistence record with no business behavior, and keeping it next to the port means Phase 4 imports one module.
