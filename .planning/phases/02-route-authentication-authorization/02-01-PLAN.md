Let coaches and admins sign in, and put their studies into the access token (D-01, D-03, D-05, ADR 0006).

Purpose: no coach can use the dashboard until the API lets a user without a participant log in, and study-scoped authorization (plan 02-04) reads the `coach_studies` claim minted here.
Output: `coach_studies` on the token service, one shared login-eligibility predicate used by send, verify and refresh, and tests for each.
</objective>

Facts verified by the planner against the current tree:
- `AuthService._eligible_login_user` holds the guards `if not user.verified_id:` and `if not self._participant_pid(user):`; `verify_login_code` repeats them in one compound `if`.
- `_issue_credential` and `refresh_token` both call `mint_access(user_id=..., participant=..., roles=self._roles_list(user))`.
- `refresh_token` computes `participant = result.participant_id or self._participant_pid(user)`, which pins the claim from the session.
- `refresh_token` calls `self._session_store.consume_for_rotation(...)` first and reads the user after it. A second presentation of a rotated token raises `RefreshReuse` and revokes the family, which already answers the uniform 401.
- `_issue_credential` and the OTP and session stores already accept `participant_id=None`; `auth/schemas.py` declares `PrincipalSummary.participant: str | None`.
- `MongoUser.roles` is `Any`, so stored study ids may not be plain strings. The API may not import `bson` (`test_source_invariants.py`), so derive with `str(s)` and never type-check for ObjectId.
- `conftest.py` provides `fakes`, `app`, `client`, `fake_email_sender`; `FakeEmailSender.last_code(email)` returns the code.
