Do not edit `tests/test_policy_matrix.py` or `authz/engine.py`: four other plans run beside this one, and `ROLLED_OUT` detects a router on its own. If the engine appears wrong, stop and report it rather than editing it here.

Facts verified by the planner against the current tree:
- `participant_group.py` `_fetch` calls `check_parent` on owner, and `list_items` calls `repo.get_for_owner_between`, which `CBParticipantGroupRepository` does not implement (it raises on a live store). `ParticipantGroup.participant_ids` is a `list[str]`; `list_all` exists on every adapter.
- `ParticipantGroup` is a `BaseOwnerEntity`, so `created_at` is an epoch float. `resolve_time_range` returns Arrow values.
- `conversation.py` `create` builds `ConversationEntity(**body.model_dump(exclude_unset=False))` with no audit stamp, so `BaseOwnerEntity.__post_init__` writes `updated_by = owner`. `ConversationCreate` takes `owner` and `study_id` from the body. `:search` calls `repo.get_for_filters(filters)`.
- `schemas/fitbit.py` `Fitbit` has optional `access_token` and `refresh_token`, with wire keys `accessToken` and `refreshToken`. `serialize_one` returns a dict of wire keys.
- `Device.participant_id` and `Fitbit.participant_id` hold the participant id.
