<objective>
Keep staff out of the participant app with a clear message, without leaving a token behind, and prove the client's bearer behavior for the enforced API (D-02, D-11, AUTH-09).

Purpose: D-01 lets coaches obtain tokens, so a coach who signs in on a phone would otherwise reach a participant-only app. This mirrors the dashboard's gate in the other direction. It is UX only; the API stays the security boundary, and no wire change is made.
Output: a repository gate, a new `AuthError` variant with its string, and two Kotlin host tests.

Scheduling: this plan's only code dependency is plan 02-01. The edges on plans 02-05 to 02-09 are scheduling edges that place it in Wave 5, because the execution index derives waves from `depends_on`. Its precondition stops for a human until the developer has done the setup in `user_setup`, which is not done at planning time, so all backend work finishes first. This is a local gate by developer decision on 2026-11-04: CI running the same command does not replace it.
</objective>
